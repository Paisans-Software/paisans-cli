# Backups to S3

Date: 2026-10-11. Status: design approved by the founder in session; this
written spec awaits review.

`README.md`, "Backup and restore", says what `paisans backup` must produce:
the declaration, the secrets, the databases and the object storage, with the
age keys as a fifth thing kept elsewhere. Nothing implements it. This spec is
the design for it: unattended, incremental backups of every app's databases,
files and configuration to one or more S3 compatible destinations, on a
cadence and retention the operator declares, and the commands that restore
from them.

## Scope

In:

* a `metadata:` block in `paisans.yaml`, with a revision that every toolkit
  write bumps, and `apply` copying the declaration and the secrets file to
  every site;
* a `backup:` section in `paisans.yaml` and the `validate` rules for it;
* WAL-G for every Postgres: Spilo's bundled WAL-G for the cluster, a new
  `postgres-walg` image for every pinned Postgres;
* a per site backup runner, `paisans-backup`, that backs up what is not
  Postgres with restic, enforces retention, copies Postgres backups between
  destinations and reports to the monitor;
* `paisans backup status | run | verify | restore | drill`.

Out, each its own spec:

* **A backup target for home hardware.** A separate Paisans-Software project
  that runs its own Garage on a home machine, a VM or a NAS as a backup
  destination. It is never the run time Garage cluster. To this design it is
  one more S3 endpoint.
* **Destination health monitoring.** Detecting that a destination has been
  unreachable for a long time is a separate monitoring feature. The runner
  reports its own failures (see *Reporting*); it does not watch destinations
  between runs.

## Goals

Founder requirements, from the session:

* **Any S3 endpoint.** The toolkit names no provider. Each destination is an
  endpoint, a bucket and credentials.
* **More than one destination.** Eg: Backblaze B2 and a home Garage. Each
  destination is backed up independently and keeps its own retention.
* **Incremental.** Only what changed is uploaded, and as far as the tools
  allow, only what changed is read. A database growing to terabytes must not
  turn the nightly backup into a maintenance problem.
* **Cadence the sysadmin declares.** Daily, weekly, monthly or yearly runs.
* **Retention by cycles per tier.** Eg: keep 7 daily, 3 weekly, 2 monthly,
  1 yearly.
* **Pruning is on by default**, and declared per destination in
  `paisans.yaml`.
* **Backups are on by default.** A deployment without backups says so
  explicitly.

## What gets backed up, and by whom

Every piece of state has exactly one owner, so no two sites back up the same
thing. The owner is either the cluster (whichever site holds the Patroni
leader) or the one site an app is pinned to.

| State | Owner | Tool |
|-------|-------|------|
| The Postgres cluster: every clustered app's database (Eg: Mbin, Outline, WriteFreely, Pocket ID) | the Patroni leader, natively | WAL-G in Spilo |
| A pinned app's Postgres (Eg: Synapse and MAS, a pinned Mbin) | its site | WAL-G in `postgres-walg` |
| Uptime's SQLite | its site | `sqlite3` consistent copy, then restic |
| A pinned app's authoritative files (Eg: Synapse's media store, Uptime's `data/`) | its site | restic |
| Garage buckets (every app's uploads) | the runner on the leader's site | `rclone sync` to a local mirror, then restic |
| `paisans.yaml` and `secrets.enc.yaml` | the runner on the leader's site | restic, and a raw age encrypted copy (see *Recovery kit*) |

### Why clustered apps put nothing on this list from disk

A clustered app runs on several sites at once, so the placement rules already
require its authoritative state to live in Postgres or Garage. Its bind
mounts are rendered by `apply` from the secrets (Eg: Mbin's `oauth/`
keypair, every `.env`), are caches and runtime state that rebuild themselves
(Eg: Caddy's certificates, Mercure's bolt database, RabbitMQ's queue, Pocket
ID's `run/` standby marker), or are unused while uploads go to S3 (Mbin's
`media/`). None is backed up. Backing them up from every site would only
produce duplicates of things `apply` recreates.

Each kind therefore declares its backup paths **per placement**, in
`internal/kinds`, beside its services and volumes. A `cluster` placement
declares none. A test fails if any kind declares a disk path for `cluster`,
so a new kind cannot introduce a duplicate.

Pocket ID stores uploads in its database (`FILE_BACKEND=database`, the
toolkit's default). Whether any Pocket ID version keeps signing keys under
`data/` is to be verified against upstream in phase 4; if one does, those
keys are rendered from secrets or declared as a pinned path, never left
unowned.

## `paisans.yaml`

### `metadata:`

`version` and `id` move from the top level into a `metadata:` block, joined
by a revision and a timestamp:

```yaml
metadata:
  version: 1
  id: 7f3c9a52-0d1e-4b8a-9c4f-2a6e8b1d5f70
  revision: 42
  updated: 2026-10-11T18:04:00Z
```

The file format breaks; the schema version does not change, because there is
no deployment to carry across. Founder decision. A file with `version` or
`id` at the top level is refused with a message naming the move.

**`revision` versions the pair**, `paisans.yaml` and `secrets.enc.yaml`
together. Every toolkit command that writes either file bumps `revision` and
sets `updated` (UTC): `init`, `apply`, `secrets set`, `storage init`,
`storage rotate-key`, and anything that records a value (Eg: an OIDC client
ID). All of them write through one helper in `internal/config`, and a test
fails if a command writes either file another way. A human editing the file
by hand does not bump it; the next `apply` sees the content changed against
the last copy it distributed, and bumps it then.

### Every `apply` distributes the pair

Every `apply`, including `apply --site <name>`, copies both files to every
site at `/srv/paisans/<token>/config/`, owned by root, mode 0600. A site
that cannot be reached is a warning, not a failure, and is caught up by the
next `apply`. `secrets.enc.yaml` stays age encrypted on the host; no key
reaches a host, as `AGENTS.md` requires. Each site therefore holds a
declaration it can name by revision, and the runner tags what it backs up
with that revision.

### `backup:`

```yaml
backup:
  enabled: true              # only an explicit false turns backups off
  schedule: daily            # daily | weekly | monthly | yearly
  at: "03:00"                # UTC
  postgres:
    delta_max_steps: 6       # WAL-G deltas between full base backups
  destinations:              # the first is the primary; see below
    - name: b2
      endpoint: https://s3.us-west-004.backblazeb2.com
      region: us-west-004
      bucket: example-backups
      prefix: paisans        # optional
      prune: true            # optional, default true
      keep: { daily: 7, weekly: 3, monthly: 2, yearly: 1 }
      verify_fraction: 12    # optional: read 1/12 of the data each week
      upload_limit_kib: 0    # optional, 0 is unlimited
    - name: home
      endpoint: https://s3.home.example.org
      region: garage
      bucket: paisans
      keep: { weekly: 4, monthly: 12, yearly: 3 }
```

**The first destination is the primary.** Postgres streams its write ahead
log to it continuously; the others receive copies after each run (see
*Postgres*).

**Schedule and retention are separate.** `schedule` says how often a run
happens. `keep` says how many of each period's newest backup survive. A
daily schedule with `keep: { daily: 7, weekly: 3 }` runs every night, keeps
the last seven, and keeps the newest of each of the last three weeks. This is
restic's own model (`restic forget --keep-daily` and the rest).

**Secrets.** Per destination, `backup.destinations.<name>.access_key_id` and
`.secret_access_key`, pasted with `paisans secrets set`; `init` lists them as
owed. `backup.restic_password` and `backup.walg_libsodium_key` are generated
by `init` and never seen.

### Validation

Refused:

* no `backup` section at all. Backups are on by default, so a declaration
  must either configure them or say `enabled: false`;
* `enabled: true` with no destinations;
* a destination without `endpoint`, `bucket` or `region`;
* two destinations with the same `name`;
* a destination whose credentials are missing from the secrets;
* `prune: true` with an empty `keep`;
* a `keep` tier finer than `schedule` (Eg: `keep.daily` with
  `schedule: weekly`), since it can never be filled;
* `at` that is not `HH:MM`.

Warned:

* `enabled: false`;
* `prune: false`, since that bucket only grows;
* a single destination, since one provider is one failure domain;
* no `uptime` app, since nothing will page anyone when a run fails.

## Postgres

### The cluster: Spilo's WAL-G

Spilo bundles WAL-G (v3.0.8 in `spilo-18:4.1-p2`, `Dockerfile`
`ENV WALG_VERSION`) and turns it on when `WALG_S3_PREFIX` is set
(`postgres-appliance/scripts/configure_spilo.py`). `apply` renders, into
`patroni.env`, the primary destination's prefix and credentials,
`AWS_ENDPOINT`, `AWS_REGION`, `AWS_S3_FORCE_PATH_STYLE=true`,
`WALG_LIBSODIUM_KEY`, `WALG_DELTA_MAX_STEPS`, `BACKUP_SCHEDULE` from
`schedule` and `at`, and `WALG_NETWORK_RATE_LIMIT` from the primary's
`upload_limit_kib`.

**Leader only, and it follows failover, without anything from us.** Spilo
sets `archive_mode: on`, and Postgres archives only on the primary with that
setting (PostgreSQL documentation, `archive_mode`). Spilo's cron runs
`postgres_backup.sh` on every node, and the script exits when
`pg_is_in_recovery()` is true (`postgres-appliance/scripts/postgres_backup.sh`).
Whichever site Patroni promotes takes over archiving and base backups.

**Incremental.** With `WALG_DELTA_MAX_STEPS` above zero, a base backup is a
delta: a data file whose modification time matches the previous backup is
skipped without being read, and from a changed file only pages at or past the
previous backup's LSN are uploaded (`internal/databases/postgres/bundle.go`,
`incremental_page_reader.go`). A full base backup happens every
`delta_max_steps + 1` runs. Between base backups the write ahead log streams
continuously, which also gives point in time recovery to any moment inside
the daily tier, not only to the nightly backup.

**Spilo's own pruning is neutralised.** `postgres_backup.sh` deletes backups
older than `BACKUP_NUM_TO_RETAIN` (at least that many, at least that many
days old). The toolkit sets it high enough never to fire, and the runner owns
retention (see *Retention*). Phase 3 verifies that this leaves Spilo deleting
nothing.

### Pinned Postgres: `postgres-walg`

WAL-G publishes no Postgres image, and its release binaries are glibc linked,
so they do not run on the `-alpine` images pinned apps use today (`file` on
the v3.0.8 binary). Every pinned Postgres moves to
`ghcr.io/paisans-software/postgres-walg:<major>`: Debian's `postgres:<major>`
plus WAL-G built with libsodium, published from this repository's image
workflow for each major the catalogue uses (16, 17, 18), rebuilt when either
upstream releases. Founder decision.

It is configured like Spilo: `archive_mode=on`,
`archive_command='wal-g wal-push %p'`, `archive_timeout=1800`, and a small
scheduler in the image running `wal-g backup-push` on the same `schedule`,
since a delta backup must run beside the data directory (WAL-G
`docs/PostgreSQL.md`, "Remote backup"). Each pinned app gets its own prefix.

A data directory created under Alpine is not reused under Debian: the two C
libraries collate text differently, so text indexes built under one can
mis-sort under the other. New deployments start on Debian; the toolkit does
not convert an Alpine data directory.

### Prefixes

```
<prefix>/<deployment id>/pg/cluster/       the Spilo cluster
<prefix>/<deployment id>/pg/<app>/         each pinned Postgres
<prefix>/<deployment id>/restic/           the restic repository
<prefix>/<deployment id>/config/rev-<n>/   raw age encrypted declaration
```

### More than one destination

WAL-G writes to one storage. Its multi storage feature fails over rather than
copying, is marked experimental, and Spilo's environment allowlist does not
pass it (`docs/FailoverStorages.md`; `configure_spilo.py`). So the primary
receives the live stream, and after each run the runner, on the owner's site,
runs `wal-g copy` from the primary to every other destination. A secondary is
therefore at most one cycle behind, and keeps its own retention.

## The runner

`paisans-backup` is a Go binary in an image of the same name, with restic,
rclone, WAL-G and sqlite3, built and pinned by digest like every other
image. One instance runs on every site, in the infrastructure stack beside
the heartbeat. It is Go because the governance below needs tests that prove
every write it can make.

It decides nothing on its own. `apply` renders a per site
`backup-plan.json` listing what the site owns, the destinations, their
`keep`, and the monitor to push to; credentials arrive in the rendered
`.env`.

### One run

At `at` on the declared `schedule`:

1. **Leader check.** `GET /leader` on the local Patroni REST API answers 200
   only on the leader. The leader's runner owns the cluster's work; every
   runner owns its site's pinned work.
2. **Stage.** `sqlite3 VACUUM INTO` for each SQLite database; `rclone sync`
   of each bucket to a persistent local mirror (only new and changed objects
   download). Before staging, it refuses if free disk is under twice the
   largest staged item, and reports the refusal.
3. **Back up**, to each destination independently, so one unreachable
   destination does not stop the others. restic snapshots carry the item and
   the declaration's revision as tags.
4. **Copy Postgres.** For each WAL-G prefix this site owns, wait for the
   run's base backup to appear on the primary, then `wal-g copy` it to every
   other destination.
5. **Retention**, per destination with `prune: true` (see *Retention*).
6. **Report** (see *Reporting*).

**Logical hosts.** restic groups snapshots by host for retention. The runner
sets the host to `cluster` for the cluster's items and to the app's name for a
pinned app's, never to the machine's hostname, so a failover or an
`app move` does not split an item's history in two.

**A failover during a run** can let two sites both believe they are the
leader for a moment and back up the same item twice. That is harmless:
restic deduplicates, retention counts periods rather than snapshots, and
restic's exclusive lock serialises pruning.

**Resources.** The container is limited to one CPU and runs its work under
`nice 10` and `ionice -c3`, so apps win every contest for CPU and disk.
`upload_limit_kib` passes to restic's `--limit-upload` and WAL-G's
`WALG_NETWORK_RATE_LIMIT`.

### Retention

restic: `restic forget --group-by host,tags` with the destination's `keep`
nightly, which touches metadata only, and `--prune` weekly, since pruning
repacks partly used pack files and costs download and upload on a paid
provider.

WAL-G has no daily, weekly, monthly or yearly retention; `delete retain`
counts backups. The runner builds it from WAL-G's own primitives:

1. For each tier above daily, the newest backup in each of the last `keep.<tier>`
   periods (UTC calendar weeks, months, years) is that period's
   representative.
2. Representatives are marked permanent with `wal-g backup-mark`; a marked
   backup that is no longer any tier's representative is unmarked
   (`backup-mark -i`). Marking a delta protects the chain it depends on.
3. `wal-g delete retain <keep.daily> --confirm`, then
   `wal-g delete garbage --confirm`.

A marked backup keeps only the write ahead log from its own start to its own
finish (`internal/databases/postgres/delete_util.go`), so weekly, monthly
and yearly backups restore to the point they were taken, and point in time
recovery covers the daily tier. Representative selection is a pure function
of the backup list and the date, tested on its own.

### Integrity

Weekly, from the owner's runner, per destination:

* `restic check --read-data-subset=n/<verify_fraction>`, rotating `n` so the
  whole repository is read once every `verify_fraction` weeks;
* `wal-g wal-verify integrity` for each prefix, so a gap in the archived log
  is found before it is needed.

### Reporting

Each runner pushes to a heartbeat monitor per site, named and seeded
like the existing per site heartbeat (`docs/specs/2026-10-07-uptime-monitoring.md`,
amendment of 2026-10-09), with an interval of the schedule plus a grace. The
push carries ok or failed and names the destination and item that failed.
The cluster's archive status (`pg_stat_archiver`: last failure, last
success) is part of the leader's report, so a stalled archive pages someone
before `pg_wal` grows into a problem. Every write the runner makes is logged
(see *Governance*).

## Load

Measured against a small production deployment in October 2026: about 200 MB
of databases and 250 MB of files on four cores, where every step finishes in
seconds.

At scale the design keeps the nightly cost proportional to change, not to
size:

* **Postgres:** a delta base backup reads only data files that changed and
  uploads only changed pages; a full base backup reads everything once every
  `delta_max_steps + 1` runs, rate limited. The write ahead log uploads
  continuously in 16 MB segments, compressed.
* **Files and mirrors:** restic skips unchanged files by metadata without
  reading them. The bucket mirror costs disk equal to the buckets on the
  leader's site, and after a failover the new leader downloads it once over
  the mesh.
* **Pruning and checks:** weekly, with network cost bounded by
  `verify_fraction` and restic's default `--max-unused 10%`.

## Recovery kit

Each run also uploads the site's `paisans.yaml` and `secrets.enc.yaml` as
plain objects under `config/rev-<n>/` in every destination, both age
encrypted, so a deployment's topology is not readable on a third party's
storage. Recovering from the loss of everything then needs only:

1. the age private key, which the toolkit already requires to be kept
   offline; and
2. access to any one destination, to read its objects.

The decrypted secrets hold the restic password, the WAL-G key and every
credential, so there is no circular dependency. `README.md`, "Backup and
restore", is updated to say this.

## Commands

All are dry runs by default, staged and gated like `site add`, and run from
the workstation. Names are provisional, as every command name in `README.md`
is.

| Command | Does |
|---------|------|
| `paisans backup status` | per destination: the newest backup of each item, its age and size, archive lag, and backups whose app or site no longer exists |
| `paisans backup run [--site]` | starts a run now |
| `paisans backup verify [--site]` | runs the integrity checks now |
| `paisans backup restore` | the four restores below |
| `paisans backup drill [--from <destination>]` | restores everything into throwaway containers on the workstation or a spare host, runs per app sanity queries, reports, removes them |

### Restore

| Scenario | How |
|----------|-----|
| One app's data is bad | restore the cluster to a scratch instance at the requested time, `pg_dump` that app's database, replace the live one; restic restores its files and its bucket |
| The cluster is lost, the sites are not | Spilo bootstraps a new cluster from the backup: `CLONE_METHOD=CLONE_WITH_WALG`, `CLONE_TARGET_TIME` (`configure_spilo.py`, `bootstrap/clone_with_walg.py`) |
| A pinned app is lost | `postgres-walg` fetches the base backup and replays the log to the requested time; restic restores its files |
| Everything is lost | fetch and decrypt `config/` from a destination, `apply` to new hosts with databases bootstrapped from the backup, restic restores the buckets and files, then the apps start |

WAL-G backs up a whole Postgres cluster, not one database, which is why a
single clustered app is restored through a scratch instance.

## Governance

Deleting backups is in the tier that needs a human present, in the
deployment agent rules and in a community's own rules. The runner deletes
backups, so it is a service the stack runs, approved once when the founder
approves this design, on these conditions: every kind of write it makes is
named here and in a decision record, its tests fail on any other write, and
it logs every write. Its complete list of writes:

1. creating backups in the declared destinations: restic snapshots, WAL-G
   base backups and log segments, `wal-g copy`;
2. uploading the encrypted `config/` objects;
3. deleting, only where `prune: true` and only by that destination's
   `keep`: `restic forget` (and `--prune`), `wal-g backup-mark` and its
   inverse, `wal-g delete retain`, `wal-g delete garbage`.

Declaring `keep` in `paisans.yaml` is the approval for that destination's
deletions. Founder decision, pending the record in `docs/decisions.md`.

Never automatic:

* **A destination removed from `paisans.yaml`** is no longer written to.
  Nothing in it is deleted.
* **An app removed** stops being backed up; its backups stay and `status`
  lists them. Deleting them is a human act.
* **`restore` against live sites** is run by a human. An agent may run its
  dry run, and may run `drill`, which touches no live data.

## Testing

* `validate` fixtures for every refusal and warning above.
* Golden renders: the runner's compose service, `postgres-walg` services,
  Spilo's WAL-G environment, each site's `backup-plan.json`; and the existing
  determinism test over them.
* The runner against fake `restic`, `wal-g` and `rclone` binaries that record
  their arguments: leader and pinned ownership, independent destinations,
  logical hosts, and that the only deletions are the ones listed in
  *Governance*, with the declared `keep`.
* Representative selection as a pure function: period boundaries, missed
  runs, year rollover, a backup aging out of one tier and into none.
* The single write path for `paisans.yaml` and `secrets.enc.yaml`.
* Integration, behind a `backup_integration` build tag, in Docker: Garage as
  the destination, a single node Spilo and a `postgres-walg`; back up, write
  rows, restore to a timestamp, run a drill. Backblaze B2 is a manual
  checklist, not CI.

## To verify during implementation

Upstream facts this design relies on that were not confirmed by reading
source, each settled in the phase that first needs it:

* that WAL-G as bundled in Spilo is built with libsodium; if not, a decision
  is needed before phase 3 (phase 3);
* that a large `BACKUP_NUM_TO_RETAIN` leaves Spilo deleting nothing, and that
  its deletion respects permanent backups (phase 3);
* that Garage accepts every request WAL-G and restic make, including any
  checksum headers (phase 3, integration test);
* Backblaze B2's intermittent multipart failure with WAL-G, fixed upstream on
  2026-10-03 (WAL-G pull request 2625) and not yet released; until a release
  carries it, `S3_ADDITIONAL_RETRYABLE_ERROR_CODES=InvalidRequest` is the
  documented mitigation, itself untested (phase 3);
* whether any Pocket ID version keeps keys under `data/` (phase 4).

## Phases

Each phase is shippable on its own and is its own pull request.

1. `metadata:`, the revision helper, and `apply` distributing the pair.
2. The `backup:` schema and its `validate` rules.
3. `postgres-walg`, and Spilo's WAL-G environment.
4. The runner image, `backup-plan.json`, scheduling, reporting.
5. Retention and copies between destinations.
6. `paisans backup status`, `run`, `verify`.
7. `paisans backup restore` and `drill`.
